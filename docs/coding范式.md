# coding 范式

> 适用目标：本文件用于辅助后续 AI 应用、Agent、RAG、后端服务类项目开发。每次启动新项目、接手旧项目、重构模块或让 AI 参与编码前，建议先让 AI 阅读本文档，再读取项目自身的 `README`、架构文档、接口文档和测试说明。

## 一、核心原则

### 1. 先显式化系统知识，再开始编码

AI 参与开发时最大的问题不是“不会写代码”，而是缺少系统上下文。资料中反复强调：真实项目里的关键知识往往存在于团队经验、历史决策、接口约定、数据库约束和运行状态中，如果不显式写出来，AI 只能靠局部代码推断，容易做出“语法正确但系统不对”的修改。

项目开始前必须先准备以下信息：

- 业务目标：这个系统解决什么问题，核心用户是谁，主要业务流程是什么。
- 架构边界：系统分为哪些模块，每个模块负责什么，不负责什么。
- 数据边界：哪些表、字段、缓存 key、文件、索引由哪个模块维护。
- 接口契约：接口入参、出参、错误码、幂等要求、超时策略和兼容性要求。
- 运行事实：核心链路耗时、错误率、关键日志字段、常见失败原因。
- 验证标准：什么算完成，必须跑哪些测试，哪些指标不能下降。

结论：AI 不是先写代码再修正，而是先读事实、定边界、写方案，再进入实现。

### 2. 文档不是越多越好，而是要能被检索、能被执行、能被校验

AI 友好的文档不是大而全的长文，而是结构化、分层、可路由的工程资产。建议采用“入口短、分层清、按需读”的方式：

- `AGENTS.md` 或 `AI_GUIDE.md`：100 行以内，只做入口索引和全局规则。
- `docs/architecture.md`：说明系统分层、模块职责、核心链路和依赖关系。
- `docs/service-card.md`：说明单个服务的接口、数据、任务、发布和验证方式。
- `docs/domain-model.md`：说明核心实体、状态机、不变量和业务约束。
- `docs/evaluation.md`：说明评测集、指标、运行方式和回归规则。
- `docs/decisions/`：记录重要技术决策，包含背景、方案、取舍和后续影响。

文档必须随代码变更同步更新。新增接口、字段、消息、配置、状态流转、评测规则时，都要同步更新对应文档，否则 AI 下一次读取的上下文会过期。

### 3. 架构约束要前置，不能只靠事后检查

AI 开发容易追求“最快实现”，因此项目需要提前写明不可违反的边界：

- Controller / API 层只做参数校验、协议转换和响应封装。
- Service / Application 层负责编排业务流程，不直接散落数据库细节。
- Domain 层维护核心规则、状态流转和业务不变量。
- Repository / Infrastructure 层封装数据库、缓存、外部服务和文件系统访问。
- Tool / Skill 层必须有输入 Schema、输出 Schema、错误分类和调用记录。
- RAG / Agent 链路必须保留 trace、source、耗时、token、缓存命中、失败原因。

如果项目是小型应用，也不必过度设计，但至少要保证“入口、业务、数据、AI 链路、评测”五类代码不要混在一个文件里。

## 二、AI 协作开发标准流程

### Phase 0：任务澄清

AI 接到任务后，必须先回答：

- 这次要解决的业务问题是什么。
- 涉及哪些模块、接口、数据表、配置和外部服务。
- 哪些部分可以直接改，哪些部分需要先确认。
- 完成后的验收标准是什么。
- 是否需要新增测试、文档或评测用例。

如果任务描述不完整，先基于代码和文档寻找答案；仍然缺失时再向人确认。

### Phase 1：上下文读取

读取顺序建议固定为：

1. `AGENTS.md` / `AI_GUIDE.md`：了解项目规则和入口。
2. `README.md`：了解启动方式、依赖和基本结构。
3. `docs/architecture.md`：了解系统边界和模块职责。
4. `docs/domain-model.md`：了解业务实体和状态流转。
5. `docs/evaluation.md`：了解测试和评测标准。
6. 当前任务相关代码：只读相关路径，避免无目标全局阅读。

读取后必须输出简短理解：本次修改落在哪一层，为什么在那里改，是否会影响上下游。

### Phase 2：方案设计

编码前先给出可执行方案，至少包含：

- 修改范围：具体文件、模块、接口或数据表。
- 数据流：输入从哪里来，经过哪些处理，输出到哪里。
- 状态流：任务状态、会话状态、工具调用状态如何变化。
- 异常流：空输入、超时、外部依赖失败、输出格式错误时如何处理。
- 验证方式：单测、接口测试、端到端评测、手工检查清单。

方案不要只写“优化 RAG”或“接入 Agent”。要明确到 planner、retrieval、reranker、context builder、generator、tool registry、memory store 等具体层次。

### Phase 3：小步实现

实现时遵循以下规则：

- 一次只解决一个目标，避免顺手重构无关模块。
- 优先复用项目已有工具、类型、错误处理和日志格式。
- 新增函数必须有清晰输入输出，复杂逻辑拆成可测试的小函数。
- 涉及模型输出时必须做结构化校验，不直接信任自由文本。
- 涉及状态变更时必须记录 run_id / task_id / user_id / trace_id 等追踪字段。
- 涉及外部服务时必须处理超时、重试、限流和降级响应。

### Phase 4：验证与回归

每次实现后必须形成验证闭环：

- 静态检查：类型检查、格式检查、lint。
- 单元测试：覆盖核心函数、边界输入和异常路径。
- 集成测试：验证 API、数据库、缓存、模型调用或工具调用链路。
- 评测用例：RAG/Agent 项目要保留 golden set，覆盖核心业务问题。
- 结果说明：说明跑了什么、通过了什么、没跑什么、剩余风险是什么。

没有验证结果的“完成”不算完成。

## 三、项目知识库组织范式

### 1. Architecture Map

Architecture Map 是系统级地图，用于告诉 AI “系统为什么这样组织”。建议包含：

- 业务域划分：例如用户、订单、文档、任务、报告、后台管理。
- 服务分层：网关层、BFF 层、应用层、领域层、基础设施层、AI 链路层。
- 核心链路：一次用户请求从前端到后端、数据库、模型、缓存和返回的完整路径。
- 依赖拓扑：同步接口、异步消息、数据库、缓存、对象存储、模型服务。
- 数据所有权：每张核心表、每个索引、每个缓存 key 由哪个模块写入和维护。
- 风险等级：哪些链路是核心链路，哪些变更需要人工确认。
- 演进方向：哪些模块是旧逻辑，只维护不扩展；哪些模块是目标架构。

### 2. Service Card

每个服务或核心模块建议维护一张 Service Card：

```yaml
service: document-rag-service
owner: ai-app-team
responsibility:
  - 文档解析
  - chunk 生成
  - embedding 入库
  - 检索召回
upstream:
  - web-api
  - admin-console
downstream:
  - postgres
  - vector-store
  - llm-provider
core_tables:
  - documents
  - document_chunks
  - chat_messages
key_apis:
  - POST /api/documents/upload
  - POST /api/chat
quality_gates:
  - 文档解析失败必须返回明确状态
  - 向量维度必须和数据库字段一致
  - 回答引用必须能回溯 source
```

Service Card 的价值是让 AI 进入某个模块前先知道“我是谁、我依赖谁、谁依赖我、我怎么验证”。

### 3. 业务知识分层

复杂业务知识不要全部塞进一个大文件。建议按变更频率和读取粒度拆分：

- 稳定层：业务实体、核心公式、状态机、长期不变的规则。
- 时效层：近期策略、活动规则、版本差异、阶段性口径。
- 场景层：典型用户流程、页面到接口映射、常见问题路径。
- 历史层：重要决策、踩坑记录、复盘结论和迁移背景。

读取时只加载当前任务需要的层。简单接口改动不需要加载所有历史材料；复杂状态机变更必须加载稳定层和历史层。

## 四、Agent / RAG 应用架构范式

### 1. 推荐分层

一个可落地的 AI 应用建议拆成以下层：

```text
frontend / client
  用户交互、流式展示、引用高亮、状态反馈

api layer
  鉴权、参数校验、请求编排、错误响应

application service
  业务流程编排、任务状态、异步调度

agent harness
  工具注册、模型调用、上下文组装、循环控制、事件流、检查点

rag pipeline
  query rewrite、retrieval、rerank、context compression、generation、citation

memory / state store
  会话消息、用户偏好、任务状态、工具调用、评测记录

data layer
  PostgreSQL、pgvector、Redis、对象存储、文件索引

evaluation / observability
  trace、日志、指标、评测集、质量报告、成本统计
```

小项目可以合并物理目录，但逻辑边界要保留。

### 2. RAG 链路标准

RAG 不只是“文档入库 + 向量检索 + 模型回答”。完整链路应包含：

- 文档解析：支持 PDF、Markdown、网页文本或业务文档，记录解析状态和失败原因。
- 文本切分：按语义、标题、段落或固定窗口切分，保留 page、section、bbox、source_id 等元数据。
- 向量生成：校验 embedding 维度、模型版本、批量入库状态和失败重试。
- 索引维护：支持新增、更新、删除、版本回滚和内容 hash 去重。
- 查询改写：对模糊问题补全领域词、同义词和上下文限定。
- 召回策略：TopK 向量召回可与关键词检索组合，避免只靠单一路径。
- 精排与去重：基于相似度、来源多样性、段落位置和重复文本过滤上下文。
- 上下文组装：按“当前问题 + 近期对话 + 证据片段 + 输出规则”构造 Prompt。
- 生成与引用：回答必须绑定 source，前端能定位到原文或证据区域。
- 评测闭环：记录检索命中率、引用覆盖率、回答正确率、延迟和 token 消耗。

### 3. Agent 链路标准

Agent 的核心不是让模型“自由发挥”，而是让模型在 Harness 约束下完成任务：

- Planner：将目标拆成步骤，明确终止条件。
- Tool Registry：工具名称、描述、参数 Schema、返回 Schema、风险等级、超时配置。
- Executor：执行工具调用，记录入参、出参、耗时、错误分类。
- Memory：短期消息、长期偏好、历史任务、证据引用分层存储。
- Context Builder：按任务动态装配系统规则、工具定义、相关记忆、业务证据。
- Checkpoint：保存运行状态，支持失败后从已完成步骤继续。
- Event Stream：向前端输出阶段事件、工具事件、模型输出和错误事件。
- Human Review：对高影响操作、不可自动判断的业务口径和发布类动作保留人工确认。
- Evaluator：基于结果、过程 trace 和业务规则判断是否完成。

## 五、Harness Engineering 范式

### 1. Model + Harness

资料中的共同观点是：模型只提供推理与生成能力，真正让 AI 进入工程生产的是 Harness。Harness 至少承担：

- 上下文管理：让模型在正确时间看到正确材料。
- 工具系统：让模型通过受控接口访问外部能力。
- 执行编排：让任务按阶段推进，而不是一次性生成。
- 状态持久化：让长任务可恢复、可追踪、可复盘。
- 评测验证：让输出质量可量化、可回归。
- 权限与边界：让不同风险等级的动作有不同处理方式。

### 2. Hook / Guardrail 设计

Hook 的价值是把横切规则放在框架层，而不是只靠 Prompt 提醒。常见切面：

- beforeModel：模型调用前整理上下文、压缩历史、注入规则。
- afterModel：模型返回后做结构化解析、字段校验、格式修复。
- beforeTool：工具调用前做参数校验、风险等级判断、人工确认路由。
- afterTool：工具调用后做结果裁剪、错误分类、事件记录和上下文附件更新。
- onRunEvent：统一记录状态变化、阶段事件、流式输出和运行指标。

原则：凡是可以确定性判断的规则，不要交给模型自由判断。

### 3. Loop Engineering

Loop Engineering 适合长任务、跨步骤任务和需要持续验证的任务。推荐五阶段循环：

1. Discover：读取资料、识别现状、确认边界。
2. Plan：拆解任务、定义完成条件和验证方式。
3. Execute：小步实现、记录变更和中间状态。
4. Verify：运行测试、评测和静态检查。
5. Iterate：根据结果修正计划，继续下一轮或停止。

关键约束：

- 完成条件必须可验证，例如“所有测试通过且新增接口文档已更新”。
- 每个循环必须有最大轮数或停止条件，避免无意义消耗。
- 状态必须外置到文件或数据库，不依赖模型记忆。
- 规划者、执行者、评审者可以分离，降低单一视角带来的误判。
- 长任务必须保留 Checkpoint，方便恢复和复盘。

## 六、上下文工程范式

### 1. Prompt 组装不是拼字符串，而是构造任务上下文

好的 Prompt 应该让模型同时知道：

- 角色：这次要扮演什么工程角色。
- 目标：要解决什么问题，完成标准是什么。
- 约束：哪些规则必须遵守，哪些范围不能改。
- 事实：相关代码、接口、数据库、文档和历史决策。
- 工具：可调用工具、参数格式、返回含义和失败处理。
- 输出：结果格式、字段 Schema、引用规则和验证要求。

建议使用结构化 Context Object，再渲染成 Prompt：

```yaml
task:
  goal: "实现文档问答引用定位"
  acceptance: "回答 source 可定位到原文页码和区域"
constraints:
  code_scope:
    - api/chat
    - services/rag
  output_schema: "AnswerWithSources"
context:
  recent_messages: []
  retrieved_chunks: []
  citations: []
  project_rules: []
tools:
  - name: match_document_chunks
    timeout_ms: 3000
```

### 2. 上下文压缩策略

长对话和 RAG 场景必须控制上下文大小。推荐分层处理：

- 近期消息窗口：保留最近 N 轮高相关对话。
- 长期记忆召回：按用户、任务、文档或领域召回相关历史。
- source 去重：相同文档、相同段落、相似内容只保留最有价值片段。
- 证据句裁剪：超长 chunk 只保留与问题相关的句子和引用锚点。
- 工具输出裁剪：长表格、长日志、长文本产物保留摘要和文件引用。
- 结构化摘要：对历史计划、用户偏好、已完成步骤做可追踪摘要。

注意：压缩不能丢掉可追溯信息。RAG 项目至少保留 source_id、page、section、chunk_id 或其他可定位锚点。

### 3. 成本与缓存友好

从资料中的缓存实践看，Prompt 的组织会直接影响成本和延迟：

- 稳定内容放前面：系统规则、工具定义、输出规范尽量固定。
- 易变内容放后面：用户问题、当前时间、临时检索片段放末尾。
- 追加优先：多轮对话尽量保持前缀稳定，减少中间插改。
- 工具集稳定：同一会话不要频繁改变工具定义顺序和内容。
- 排序稳定：source、工具、规则、Schema 保持确定性排序。
- 记录用量：每轮记录 input token、output token、cache hit、latency。

高缓存命中率不等于总成本一定低。还要看总输入量、检索片段长度、工具输出长度和重复上下文规模。

## 七、Skill 设计范式

### 1. Skill 不是长 Prompt，而是可执行 SOP

一个好的 Skill 应包含：

- 触发场景：什么时候应该使用，什么时候不应该使用。
- 输入要求：需要哪些上下文、文件、参数和前置条件。
- 执行步骤：按阶段描述，不写成散乱提示词。
- 工具说明：依赖哪些工具，工具失败时如何处理。
- 输出格式：结构化字段、报告格式或文件产物。
- 验收标准：如何判断 Skill 执行成功。
- 示例用例：典型成功案例、边界案例和不适用案例。

### 2. 知识组织原则

资料中的复杂业务 Skill 实践给出六条可复用原则：

- 收拢优于碎片化：一个分析场景所需知识尽量集中。
- 按变更频率分层：稳定知识和时效知识分开维护。
- 选项少、信号强：让模型每一步只做低歧义选择。
- 约束结构，释放内容：固定一级骨架，不穷举所有表达。
- 知识更新靠机制：评测、登记、校验、复测缺一不可。
- Token 经济性是架构约束：每个文件加载都要有理由。

### 3. Skill 评测

Skill 上线前必须可评测、可回归。建议目录：

```text
skills/my-skill/
├── SKILL.md
├── references/
├── scripts/
└── evals/
    ├── eval.yaml
    └── cases/
        ├── happy-path.yaml
        ├── missing-input.yaml
        └── edge-case.yaml
```

评测策略：

- expect 层：本地确定性检查，如文件存在、字段包含、退出码、JSON Schema。
- evidence 层：生成可复核证据，如 diff、trace、日志、输出文件。
- judge 层：对语义质量、业务合理性和复杂差异做评审。
- report 层：输出 HTML / JSON / JUnit，接入 CI 或人工验收。

不要只测最终答案。工具是否调用、参数是否正确、过程是否符合规则、异常是否可解释，都要进入评测。

## 八、评测与质量闭环

### 1. 指标体系

Agent / RAG 项目建议至少记录：

- 任务完成率：用户目标是否完成。
- 连续成功率：同一任务多次运行是否都成功。
- 检索命中率：期望证据是否进入 TopK。
- 引用覆盖率：回答中的关键结论是否能回溯 source。
- 工具调用正确率：工具选择、参数、执行顺序是否正确。
- 输出结构合格率：JSON、Schema、字段完整性是否达标。
- 响应延迟：首 token 延迟、总响应时间、工具耗时。
- 成本指标：input token、output token、缓存命中、调用次数。
- 稳定性指标：错误率、超时率、重试率、降级率。

### 2. 评测集建设

不要只用随机样本。推荐先做 50-200 条高质量 golden set，覆盖：

- 核心业务路径。
- 高风险状态流转。
- 常见用户表达。
- 多轮对话目标切换。
- 空召回、错召回、重复召回。
- 工具失败、参数缺失、外部依赖超时。
- 新版本、新模型、新 Prompt、新工具 Schema 的兼容检查。

成熟后再扩展分类采样集、长尾集、线上回流集和人工复核集。

### 3. Bad Case 处理闭环

每个失败样本要沉淀为可修复资产：

1. 汇总证据：用户输入、模型输出、Prompt、检索结果、工具调用、trace、耗时。
2. 收敛范围：判断问题属于意图识别、检索召回、上下文组装、工具执行、业务规则或回复生成。
3. 归因标签：为问题打上稳定标签，指向 owner 和处理动作。
4. 生成行动项：明确修什么、谁负责、怎么验收、优先级是什么。
5. 回流资产：进入评测集、知识库、规则、Skill 或文档。
6. 复测验证：同一用例必须在后续版本稳定通过。

评测平台的终点不是报告，而是把失败样本转化成下一轮迭代的质量资产。

## 九、数据库与状态设计范式

### 1. AI 应用常见表结构

建议至少考虑以下数据对象：

- `users`：用户基础信息和偏好配置。
- `documents`：文档元数据、解析状态、版本、hash。
- `document_chunks`：chunk 文本、embedding、页码、段落、引用锚点。
- `chat_sessions`：会话状态、所属用户、关联文档或任务。
- `chat_messages`：用户消息、模型回复、token、耗时、引用。
- `agent_runs`：一次 Agent 运行的目标、状态、开始结束时间。
- `agent_steps`：计划步骤、执行状态、输入输出摘要。
- `tool_calls`：工具名、参数摘要、返回摘要、耗时、错误分类。
- `memories`：用户偏好、长期事实、历史计划摘要。
- `eval_cases` / `eval_runs`：评测用例、运行记录、评分结果。

### 2. 数据库设计原则

- 内容去重：文档、chunk、岗位、网页等文本类数据要记录 content_hash。
- 状态可查：长任务要有 status、error_code、error_message、updated_at。
- 引用可追踪：回答证据要能回到文档、页码、段落或原始片段。
- 幂等可控：创建任务、写入 chunk、提交工具动作要有幂等键。
- 历史可回放：保留 run、step、tool_call、message，便于复盘。
- Schema 可演进：字段新增要兼容旧数据，核心枚举要集中定义。
- 索引要明确：高频查询字段、向量字段、状态字段和外键字段要建立索引。

### 3. PostgreSQL / pgvector 落地建议

- embedding 维度必须和数据库 vector 字段一致。
- 入库前校验空文本、空向量、维度不匹配、重复内容。
- 向量检索 RPC 要返回 chunk 文本、相似度分数和 source 元数据。
- TopK 不是越大越好，要结合上下文预算、噪声比例和引用覆盖率调参。
- 删除或更新文档时，要同步处理 chunks、embedding、索引和引用状态。
- 大量写入时使用批处理，并记录每批成功数、失败数和失败原因。

## 十、后端工程范式

### 1. API 设计

- 入参必须校验，错误响应要有明确 code、message 和可选 detail。
- 对外接口要说明是否幂等、是否可重试、超时时间和限流策略。
- 长任务接口要返回 task_id，通过轮询或事件流查询进度。
- AI 输出类接口要返回 trace_id，方便定位检索、模型和工具调用过程。
- 文件上传接口要拆分上传、解析、入库和问答状态，不要混成黑盒。

### 2. 异步任务与消息

- 文档解析、批量 embedding、报告生成、长任务 Agent 执行适合异步化。
- 每个任务要有 pending / running / success / failed / canceled 等状态。
- 任务失败要可重试，重试次数、错误原因和最后一次失败时间要记录。
- 消息消费要考虑重复投递，业务处理必须可幂等。
- 长任务前端展示建议使用 SSE 或 WebSocket 输出阶段事件。

### 3. 可观测性

日志必须结构化，至少包含：

- trace_id / run_id / session_id。
- user_id 或脱敏主体标识。
- module / operation / status。
- latency_ms / token_usage / cache_hit。
- error_code / error_message。
- tool_name / model_name / retrieval_topk。

监控看板建议包含接口延迟、模型调用耗时、检索耗时、工具调用失败率、任务成功率、评测通过率、token 消耗和缓存命中。

## 十一、性能与成本优化范式

### 1. 优先优化高频路径

不要一开始就追求复杂架构。先记录数据，再判断瓶颈：

- 如果慢在文档解析，优化解析器、并发和缓存。
- 如果慢在 embedding，优化批处理、模型选择和失败重试。
- 如果慢在检索，优化索引、TopK、过滤条件和重排策略。
- 如果慢在模型，优化 Prompt 长度、缓存命中和流式响应。
- 如果成本高，先看重复上下文和大段工具输出，再看模型单价。

### 2. Token 控制

- Prompt 必须有预算：系统规则、工具定义、历史消息、证据片段分别占多少。
- 工具输出不要原样塞入上下文，长结果用摘要 + 文件引用。
- RAG 证据按相似度、来源多样性、长度和引用价值筛选。
- 多轮对话保留近期消息，长期信息进入记忆摘要或向量召回。
- 报告生成只输入聚合统计和代表证据，不输入大批量原文。

### 3. 缓存策略

- 用户画像、文档元数据、常用检索结果可以放 Redis 或内存缓存。
- 模型 Prompt 前缀尽量稳定，提高服务端前缀缓存命中。
- RAG 检索可以缓存 query_hash、filter、topk 对应的候选集。
- embedding 结果以 content_hash 缓存，避免重复向量化。
- 缓存必须有失效策略，文档更新后要清理相关检索和上下文缓存。

## 十二、AI 读项目时的标准输入包

每个新项目建议准备以下文件，让 AI 开发前先读：

```text
.
├── AGENTS.md
├── README.md
├── docs/
│   ├── architecture.md
│   ├── domain-model.md
│   ├── service-card.md
│   ├── data-model.md
│   ├── api-contract.md
│   ├── evaluation.md
│   └── decisions/
├── src/
├── tests/
└── scripts/
```

`AGENTS.md` 推荐模板：

```markdown
# AI 开发助手说明书

## 项目概述
说明项目用途、核心用户和主要业务流程。

## 架构入口
- 架构说明：docs/architecture.md
- 领域模型：docs/domain-model.md
- 数据模型：docs/data-model.md
- 接口契约：docs/api-contract.md
- 评测规范：docs/evaluation.md

## 开发规则
- 修改前先阅读相关文档和代码。
- 只改本任务相关文件。
- 新增接口必须更新接口文档。
- 新增数据库字段必须更新数据模型文档。
- AI 链路变更必须补充评测用例。

## 常用命令
- 安装依赖：...
- 类型检查：...
- 单元测试：...
- 构建：...

## 完成标准
说明本项目每次任务完成前必须通过哪些检查。
```

## 十三、让 AI 开工的推荐提示词

后续开发项目时，可以先给 AI 这段指令：

```text
请先阅读 coding范式.md，再阅读当前项目的 AGENTS.md、README.md 和 docs 目录。
在动手前，请输出：
1. 你理解的项目架构和模块边界；
2. 本次任务会影响哪些文件、接口、数据表和 AI 链路；
3. 你的实现方案、异常处理方案和验证方案；
4. 哪些信息缺失，需要我确认。
确认方案后再开始修改代码。
```
